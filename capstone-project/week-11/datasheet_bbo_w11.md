# Datasheet for Datasets: BBO Capstone Oracle Data

**Mike Kennelly | Imperial College London | PCMLAI Capstone | April 2026**

---

## Motivation

**For what purpose was the dataset created?**
The dataset was created by Imperial College London's Black-Box Optimisation (BBO) Capstone system as a pedagogical tool for the PCMLAI programme. It provides students with a controlled sequential optimisation challenge: eight unknown oracle functions, each of which must be maximised under a strict budget of one query per week over 13 weeks.

**Who created the dataset and on whose behalf?**
The oracle functions were created by the Imperial College PCMLAI course team. Students do not have access to the underlying function definitions — each dataset row is an input coordinate submitted by the student and an output scalar returned by the portal.

**Who funded the creation of the dataset?**
Imperial College London, as part of the PCMLAI programme infrastructure.

---

## Composition

**What do the instances represent?**
Each instance represents one query evaluation: an n-dimensional input coordinate x ∈ [0,1]ⁿ paired with a scalar output y = f(x) returned by the oracle. There are eight separate datasets, one per function, with dimensionalities of 2, 2, 3, 4, 4, 5, 6, and 8.

**How many instances are there?**
As of Week 11 (April 2026), each dataset contains between 19 and 49 rows, corresponding to one query per week across 11 submitted weeks plus additional exploratory samples from earlier weeks.

| Function | Dimensions | Rows (W11) |
|----------|-----------|------------|
| F1 | 2 | 19 |
| F2 | 2 | 19 |
| F3 | 3 | 24 |
| F4 | 4 | 29 |
| F5 | 4 | 29 |
| F6 | 5 | 34 |
| F7 | 6 | 39 |
| F8 | 8 | 49 |

**Does the dataset contain all possible instances or is it a sample?**
It is a strict sample — each weekly query is one point from the continuous domain [0,1]ⁿ. The oracle's full response surface is unknown and can only be estimated from these evaluations.

**Is there any missing data?**
No. Every submitted coordinate has a corresponding oracle output. No imputation or estimation was performed.

**Are there any known errors, sources of noise, or redundancies?**
One F3 W7 input coordinate contains a value marginally above 1.0 (1.000000) due to floating-point boundary handling. This was accepted by the portal and clipped to [0,1] in GP training. No other out-of-bounds values exist. Oracle outputs are deterministic — the same coordinate always returns the same value.

**Is the dataset self-contained?**
Yes. The `.npy` files contain all inputs and outputs. No external data sources are referenced. The `week_log_FX.json` files contain only portal-returned scores and are used for visualisation only — they do not feed the GP training pipeline.

## Collection process

**How was the data associated with each instance acquired?**
Each input coordinate was generated by the optimisation pipeline (Steps 8–10 of the notebook) and submitted manually to the Imperial College BBO portal. The oracle score was returned by the portal and recorded in the output `.npy` file. No automated data collection occurred — every submission was a deliberate human-approved query.

**What mechanisms or procedures were used to collect the data?**
1. Pipeline generates submission string (format: `x1-x2-...-xn` to 6 decimal places)
2. Student copies string into portal interface
3. Portal returns scalar score
4. Score is appended to `f{n}_w{week}_outputs.npy` alongside the coordinate in `f{n}_w{week}_inputs.npy`

**Over what timeframe was the data collected?**
January 2026 – April 2026, one query per function per week across 11 weeks of active submission.

**Were any ethical review processes conducted?**
Not applicable — this is a course-controlled pedagogical dataset with no human subjects or sensitive personal data.

## Preprocessing, cleaning, and labelling

**Was any preprocessing or cleaning done?**
A single clip operation is applied to input coordinates before GP training: `X_train = np.clip(X_train, 0.0, 1.0)`. This handles the one out-of-bounds value described above. No other preprocessing is applied to inputs. Outputs are used as-is from the portal.

**Was the raw data saved in addition to the preprocessed data?**
Yes. The raw `.npy` files contain unmodified portal values. The clip operation occurs inside the notebook at runtime and is not persisted to file.

**Is the data labelled?**
Not externally. Binary classification labels (`y_labels`) are derived within each notebook at runtime by thresholding outputs at the 70th percentile (top 30% = class 1, bottom 70% = class 0). These are not stored — they are recomputed each run.

## Uses

**Has the dataset been used for any tasks already?**
Yes — eleven rounds of BBO optimisation, one query per function per week. The dataset is the primary training data for the GP surrogate and binary classifier at each iteration.

**What other tasks could the dataset be used for?**
- Benchmarking GP kernel choices (Matérn 3/2 vs 5/2 vs RBF) on small-n real oracle data
- Studying the empirical relationship between n/p ratio (samples per dimension) and surrogate reliability
- Comparing acquisition function behaviour (EI vs UCB) under small-budget constraints
- Demonstrating boundary-seeking behaviour in structured black-box functions (F5, F8)

**What might impact future uses?**
- Functions are purpose-built for a course — they may not reflect industrial or scientific black-box functions
- Sample sizes (n=19–49) are extremely small relative to dimensionality (2D–8D) — models trained on this data should not be evaluated against standards set for larger datasets
- The domain [0,1]ⁿ is normalised — absolute coordinate values have no physical meaning outside the capstone context

**Are there tasks for which the dataset should not be used?**
This dataset should not be used to make claims about real-world physical or engineering systems. The oracle functions are pedagogical constructs. It should not be used to train production ML models, and the coordinate values should not be interpreted as having any physical significance.

## Distribution

**How is the dataset distributed?**
The dataset is distributed as `.npy` files in the public GitHub repository: [github.com/kennelm2025/Mikes-Capstone](https://github.com/kennelm2025/Mikes-Capstone) under `/capstone-project/week-{n}/`.

**Is the dataset subject to any intellectual property or other restrictions?**
The input coordinates were generated by the student and are freely shareable. The oracle output values were provided by Imperial College's BBO portal. Sharing the data for academic and research purposes is consistent with the course's open-knowledge ethos. The underlying oracle function definitions remain proprietary to Imperial College.

**Does the dataset contain data that might be considered confidential?**
No. The data contains only coordinates in [0,1]ⁿ and scalar oracle outputs. No personal, sensitive, or commercially confidential information is included.
